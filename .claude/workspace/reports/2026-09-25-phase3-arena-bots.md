# Phase 3 report: ML arena and bot personas

*2026-09-25, branch `experiment/enemy-ml`. Not committed yet. Plan: `plans/2026-09-24-enemy-ml-v1-rl.md`, §6 Phase 3.*

## Summary

- **The exit criterion is met.** The criterion was "each persona produces the expected profile in the profiler". It was checked twice:
  - in a pure simulation (`logic-tests.sh`, all checks pass);
  - in Unity, with 8 arenas running bots for about 40 game-minutes each, played through Unity MCP.
- **Built:**
  - the `MLArena` scene, with 8 isolated copies of an arena;
  - an input seam, so a bot drives the real `PlayerController` and `WeaponManager` under the same rules as a human;
  - 6 persona assets and a pure-logic `BotBrain`;
  - an editor builder that generates all arena assets;
  - a telemetry report tool.
- **Game bugs found** (on `main` too; not fixed, your call):
  1. The player's `WeaponManager` fires from the **prefab asset** `Weapon.prefab`, not from the Player's own weapon.
  2. The zombie attack animation has 2 events with no receiver, which logs 2 errors per zombie attack.
- **One change to the Phase 2 profiler, which needs your review.** While a player is retreating, stopping briefly to shoot now counts as Kite rather than Fight. Without this, kiting is nearly invisible, because this game doesn't allow firing while moving. The setting is `EngagementSettings.kiteGapSeconds = 1.5`; set it to 0 for the old behaviour.

**Arena layout:**
- The base is at the arena origin. It uses MainGame's base sprite and collider (5×6), but as an `ArenaBase`: it logs damage and has no game over.
- The player starts at (0, −4.5).
- Refuges sit 26 units out: A = east (red), B = north-west (green), C = south-west (blue). These are zones `E2`, `NW2` and `SW2` of the unchanged 17-zone radial map, so observations match MainGame.
- There are no walls, because baseline zombies walk in straight lines and would snag on them.
- Zombies are a variant of `001Z` with drops disabled and everything else inherited. The wave is Day 3's: 20 zombies, 5 alive at once, one every 2 s, spawned 5–15 units from the player.

**Personas** (routes A/B/C; every numeric parameter is re-sampled each episode):

| Persona | Behaviour |
|---|---|
| Fighter | Stands at the base and shoots anything within 6–9 units. Never flees. |
| RunnerA | Always flees via A (east). |
| Mixed | 60% flee / 40% fight; flees via B 70%, C 30%. |
| Adaptive | Flees; prefers A (80%); after an ambush that route's weight × 0.2, recovering 5% per clean escape. |
| Kiter | Kites; route preference C 70%. |
| Random | Equal mode and route weights, jittered up to 2× per episode, with wider reaction, aim and linger ranges. |

## Findings

1. **Weapon asset bug (game, on `main` too).** `MainGame > Player > WeaponManager.availableWeapons[0]` is `Assets/Prefabs/Weapon.prefab`, the asset, not the Player's child `Weapon`. At runtime the game fires from, and moves, the asset:
   - **In the arena**, all 8 players shared one weapon: one 5 shots/s cooldown and one magazine. Fighters died and kiters rarely fired. Fixed for the arena: the builder remaps the arena player to its own child weapon, whose combat stats are identical.
   - **In MainGame**, each play session moves the asset's `Firepoint` (observed at (468.9, −152.2) and (12.5, −15.4)). The file on disk already holds a stale (4.20, −12.63). If the project is saved after playing, `Weapon.prefab` changes. The asset's `nextFireTime` survives between plays in the same Editor session, which is very likely why `RangedWeapon` has the "abnormal cooldown" guards. Also, the asset has no `bulletItem`, so **reloads are free** and the child's inventory ammo (Bullet ×30) never applies.
   - **Suggested fix (your call, belongs on `main`):** drag the Player's child `Weapon` into `availableWeapons` in MainGame. Until then, after playing MainGame, reimport `Weapon.prefab` before saving (agents do this).
2. **Kite was nearly invisible to the Phase 2 classifier.** In this game you can't fire while moving, and each shot locks movement for about 0.42 s. So a kiter's stops to shoot were labelled Fight, and each retreat leg (under 1 s) was dropped as an escape.
   - **Change:** within an active escape, shooting while standing still for up to `kiteGapSeconds` (1.5 s) after the last retreating sample is labelled Kite, and the escape continues.
   - **Evidence (same bot and seed, in the sim):** with the gap at 0, Kite is 8% and 0 of 3 escapes are typed Kite; with 1.5, Kite is 19% and 11 of 14 are typed Kite. Other personas stay at 0% Kite either way. The Phase 2 tests still pass.
   - **Limit:** even an ideal kiter stands and shoots about half its time, so it reads as roughly Fight 45% + Kite 20%. Kite recall in Unity is 33%. Treat Kite share as a *relative* signal.
   - **Set it to 0 if you'd rather keep the Phase 2 definition.**
3. **Runners show about 40% Passive.** The label breakdown shows the tracker labelling the bot's Flee time as Flee (73%) or Passive (27%), and its Return and Linger time as Passive. This comes from the arena setup:
   - The baseline spawner keeps spawning zombies 5–15 units from the player, even at the refuge.
   - The player standing still or walking home with zombies inside 15 units is "not retreating, not shooting", which is Passive.

   This is a faithful measurement, not a bug, but it means Flee shares near 60% are "high" in this game. It also matters for Phase 4, where a commander that stops spawning around the player will change these numbers.
4. **Ambushes under Baseline are frequent.** 45 for Adaptive over 142 flees; 18 for RunnerA over 206. Ring spawns often put a zombie within 4 units ahead on the route. So Adaptive already drifts off A (64% instead of 80%) without any deliberate interception. The stronger, systematic test (a commander ambushing A) is covered in the sim and should be repeated in Unity in Phase 4.
5. **Zombie attack animation events have no receiver.** `001Z_Attack` fires `OnAttackHit` and `OnAttackComplete`, but `Enemy` implements neither. That's 2 console errors per zombie attack in MainGame and the arena. Pre-existing and harmless, but it floods the console. Fix on `main`: add empty receivers to `Enemy`, or remove the events.
6. **Fighters die in about 40% of waves** of the Day 3 horde when they only stand and shoot. Zombies do damage the player and the base in Unity; contact works despite the large colliders.

## Notes for Phase 4

- **Speed.**
  - `Time.timeScale` 8 in the Editor gave about 0.009 s of game time per frame.
  - Bots, `PlayerController` input, and `Enemy` target selection all run in `Update`, so fidelity depends on frame rate. Keep game-seconds per frame ≤ 0.02: use a high-fps standalone build (`-batchmode -nographics`), or cap the time scale.
  - The monitor already samples on `FixedUpdate`.
- **Run in background.** When Unity isn't focused, Play mode freezes unless `Application.runInBackground` is set. `ArenaManager` sets it at runtime; Player Settings are untouched.
- **Episodes.**
  - `ArenaEnvironment` resets the profile each episode (3 waves).
  - The RL agent should see the profile building up within an episode, so consider 5 or more waves per episode for training.
  - `HordeEventSpawner.AbortHordeEvent()` is the episode-termination hook.
- **What to keep in mind when choosing opponents.** RunnerA never kills, so its waves always hit the 90 s limit. The commander's reward must not depend on waves ending.
